## 検証内容と検証結果の概要

LLMを使ったアプリケーションでは、依頼内容に応じて適切なSkill（処理手順や専門知識のまとまり）を選び、そのSkillを実行LLMに渡す構成があります。
このとき、Skillの選択まで実行LLM自身に任せるのではなく、Skill選択専用のJevを前段に置くと、実行LLMの入力を小さくできるのではないかと考えました。

そこで、次の2方式を同じ依頼文・Skill一覧・Skill本文で比較しました。

| 方式 | Skillの選択 | Skillの実行 |
| --- | --- | --- |
| LLM方式 | 実行LLMがSkill一覧から選択 | 同じ実行LLMが、依頼と選択したSkillを使って回答 |
| Jev方式 | JevがSkill一覧から選択 | 実行LLMは、依頼とJevが選択したSkillだけを使って回答 |

今回の実験では、10種類のSkillを用意し、それらを使う30件の依頼を作成しました。Skillの具体的な内容と依頼例は[検証環境](#検証環境)で説明します。

30件の依頼を使った結果は、次のとおりです。

| 評価項目 | OpenAI比較 | Gemini比較 |
| --- | ---: | ---: |
| 実行LLMのトークン削減率 | **59.42%削減** | **56.25%削減** |
| Skill選択の一致率 | **96.67%（29/30）** | **100%（30/30）** |
| Jevを含む総トークン数 | **38.43%増加** | **43.25%増加** |

この結果から、Jev方式は「実行LLMに使わせるトークンを減らす」ことには効果がありました。Skillの一致率もOpenAI、Geminiともに95%以上となっており、高い確率がありました。
Jevを含んだ場合の総トークン数は、増加しているものの、Jevでの料金が安いため、総費用では、Jevと組み合わせたほうが安くなる見込みです。

## 前提：Jevとは

Jevは、TypeSafe AIが提供する「System One Model」と呼ばれる新しい種類のモデルです。一般的なLLMが文章やコードなどのテキストを生成することを得意とするのに対して、Jevはソフトウェアがそのまま利用できる、構造化された判断を高速に返すことを目的としています。

たとえば、文章で入力された状態に対して、次の処理を行うモデルとして利用できます。

- 複数の選択肢から適切なものを選ぶ
- 入力を分類する
- 処理を別の経路へ振り分ける
- 必要な情報を抽出する
- 判断の確信度や確率を返す

一般的なLLMとの違いを簡単にまとめると、次のようになります。

| 項目 | 一般的なLLM | Jev |
| --- | --- | --- |
| 主な出力 | 自由な文章やコード | あらかじめ定義した構造化データや判断 |
| 主な用途 | チャット、文章作成、コード生成 | 分類、ルーティング、抽出、条件分岐 |
| ソフトウェアとの接続 | 生成された文字列の解釈や検証が必要 | 定義済みの形式で受け取りやすい |
| 推論の特徴 | トークンを順番に生成 | 複数の判断を並列に扱う設計 |
| 判断の情報 | 回答文が中心 | 判断に加えて確率や確信度も扱う |

TypeSafe AIの紹介記事では、Jevを「非構造化の状態を入力し、型付きの確率的な判断を出力する、知能の高い関数呼び出し」のように説明しています。また、文章生成の柔軟さをあえて制限する代わりに、構造化された出力・高速な判断・ソフトウェアとの組み合わせやすさに重点を置いているとされています。詳しくは、[TypeSafe AIによるJevの紹介記事](https://typesafe.ai/blog/introducing-system-one-models-and-jev)を参照してください。

### 今回の実験でのJevの役割

今回の実験では、Jevを「ユーザーの依頼に対して、どのSkillを使うべきかを選択するルーター」として使いました。Jev自身に最終回答を書かせるのではなく、次のような役割分担にしています。

1. ユーザーの依頼とSkill一覧をJevに渡す
2. Jevが最適なSkillを1つ、または `no_skill` を選ぶ
3. 選ばれたSkill本文と依頼を実行LLMに渡す
4. 実行LLMが最終的な回答を生成する

通常のLLM方式では、実行LLMがSkill一覧を読み、選択し、その後でSkill本文を読みます。Jev方式では、実行LLMはSkill選択を担当せず、Jevが選んだSkillだけを受け取ります。そのため、実行LLMにSkill一覧を毎回入力する必要がなくなります。

今回の実験では、Skill選択と回答生成を別の処理として計測しました。Skill選択をJevに置き換えた場合に、実行LLMのトークン数・応答時間・選択品質がどう変化するかを確認するためです。

なお、実験では実行LLMとしてOpenAI APIとGemini APIを使用しました。OpenAIでは `gpt-4o-mini`、Geminiでは `gemini-3.6-flash` を使い、Skill選択専用のJevには `jev-1.13.0` を使いました。

## 検証環境

| 項目 | 内容 |
| --- | --- |
| 実行日 | 2026年9月23日（日本時間） |
| 実行環境 | macOS（Apple Silicon）、Python 3.13.5 |
| 実験プログラム | Python標準ライブラリのみで作成した検証スクリプト |
| 依頼数 | 30件 |
| Skill数 | 10個 |
| OpenAI | `gpt-4o-mini`（OpenAI API） |
| Gemini | `gemini-3.6-flash`（Gemini API） |
| Jev | `jev-1.13.0`（Jev API） |

依頼文、Skill一覧、Skill本文は両方式で固定しました。OpenAIとGeminiはそれぞれ別に実行し、APIが返した入力・出力トークン数を記録しました。時間はAPI呼び出しのネットワーク時間を含む実測値です。

用意したSkillと依頼内容の例は次のとおりです。

| Skill | 想定している作業 | 依頼内容の例 |
| --- | --- | --- |
| PDF処理 | PDFの読み取り、ページ参照、表や文章の抽出 | PDFの売上表から商品別の合計金額を抽出する |
| 文書作成 | 文書の作成、編集、校正、構成整理 | 会議メモを背景・決定事項・担当者・期限に整理する |
| 表計算 | ExcelやCSVの整形、集計、計算 | 売上データを月別に集計し、前月比を計算する |
| プレゼン資料 | スライドの構成、作成、編集 | 新製品発表会の10枚構成を作る |
| 画像生成 | 画像の生成、既存画像の編集 | 商品写真の背景を削除し、透明背景にする |
| Web調査 | 最新情報の検索、比較、出典付きの調査 | 企業の最新料金プランを公式サイトで比較する |
| OCR | スキャン画像やスキャンPDFの文字起こし | 領収書の画像から日付・金額・店舗名を読み取る |
| コードレビュー | バグ、セキュリティ、テスト不足の確認 | API変更のプルリクエストに問題がないか確認する |
| データ分析 | 傾向、外れ値、統計的な比較、可視化 | 2つの実験群の平均値に差があるか比較する |
| メール作成 | ビジネスメールの作成、要約、丁寧化 | 取引先への納期遅延のお詫びメールを作る |

このほか、Skillを使わなくても回答できる依頼として、簡単な天気の問い合わせもテストしました。特定のSkillが必要な依頼だけでなく、似たSkillのどちらを選ぶか迷いやすい依頼や、`no_skill` を選ぶべき依頼も含めています。

## 検証結果

### トークン消費量

「生成LLMのトークン削減率」は、LLM方式の選択・実行に使ったトークンと、Jev方式で実行LLMの回答生成に使ったトークンを比較したものです。

| 指標 | OpenAI | Gemini |
| --- | ---: | ---: |
| LLM方式の実行LLMトークン | 27,405 | 26,046 |
| Jev方式の実行LLMトークン | 11,120 | 11,394 |
| 実行LLMトークン削減率 | **59.42%** | **56.25%** |
| Jev方式のルーティングトークン | 26,818 | 25,918 |
| Jev方式の総トークン（Jev＋実行LLM） | 37,938 | 37,312 |

Jev方式では、実行LLMにSkill一覧を読ませて選択させる処理がなくなるため、実行LLMのトークン数は大きく減りました。ただし、Jevにも依頼とSkill一覧を渡す必要があるため、Jevのトークンを加えた単純合計は増えています。

ここでいう「トークン」は、異なるモデルの値をそのまま足し合わせたものです。JevとOpenAI・Geminiでは、tokenizerやモデルの処理内容、料金体系が異なります。そのため、総トークン数の増減はコストの増減を直接意味しません。実際の費用を比較する場合は、各APIの単価を使って別途計算する必要があります。

### Skill選択の一致率と正確さ

| 指標 | OpenAI | Gemini |
| --- | ---: | ---: |
| Jevと実行LLMの選択一致率 | 96.67%（29/30） | 100%（30/30） |
| 正解ラベルとの一致率：実行LLM | 93.33%（28/30） | 96.67%（29/30） |
| 正解ラベルとの一致率：Jev | 96.67%（29/30） | 96.67%（29/30） |

OpenAIとJevが異なるSkillを選んだのは1件でした。「売上データを月別に集計し、前月比も計算する」という依頼に対して、正解ラベルとJevは `spreadsheets`、OpenAIは `data_analysis` を選んでいます。

また、「今日の東京の天気を教えてください」という依頼では、正解ラベルを `no_skill` としていましたが、3つの選択器はすべて `web_research` を選びました。これはモデルの性能だけでなく、「最新の天気を答えるにはWeb調査Skillが必要か」という正解ラベルの定義にも関係する結果です。

### 処理時間

#### Skill選択だけの時間

| 比較 | LLM方式 | Jev方式 | Jev方式の短縮率 |
| --- | ---: | ---: | ---: |
| OpenAI・平均 | 836.59 ms | 614.20 ms | 26.58% |
| OpenAI・中央値 | 763.71 ms | 565.54 ms | 25.95% |
| Gemini・平均 | 2,071.38 ms | 582.25 ms | 71.89% |
| Gemini・中央値 | 1,431.38 ms | 580.13 ms | 59.47% |

Skill選択だけを見ると、Jev方式はOpenAI・Geminiの両方より短時間でした。特にGeminiでは、選択時間の中央値が約59%短くなっています。

#### 選択から回答生成完了までの時間

| 比較 | LLM方式 | Jev方式 | Jev方式の短縮率 |
| --- | ---: | ---: | ---: |
| OpenAI・平均 | 3,970.20 ms | 3,536.11 ms | 10.93% |
| OpenAI・中央値 | 3,665.65 ms | 3,226.52 ms | 11.98% |
| Gemini・平均 | 8,195.56 ms | 6,518.45 ms | 20.46% |
| Gemini・中央値 | 8,468.42 ms | 5,926.62 ms | 30.02% |

OpenAIは30件すべて、Geminiは29件で最後まで完了した結果を使っています。Geminiの1件（Web調査を求める依頼）は実行フェーズが空応答となったため、Geminiの回答生成完了までの時間とトークン比較から除外しました。Skill選択自体は30件すべてで成功しています。

### 検証結果の見方

今回の結果は、次のように分けて解釈する必要があります。

- 実行LLMのトークン数を減らしたい場合、Jevによる事前ルーティングは有効でした。
- Jevのトークンまで含めた生の総トークン数は増えました。
- Skill選択の品質は、OpenAI・GeminiともにJevとほぼ一致しました。
- 処理時間は、Skill選択だけでなく、回答生成まで含めてもJev方式が短くなりました。
- ただし、各依頼は原則1回の測定であり、ネットワーク状況やAPI負荷の影響は除けません。

## まとめ

30件の依頼と10個のSkillを使った今回の検証では、JevをSkill選択に使うことで、実行LLMのトークン消費をOpenAIで59.42%、Geminiで56.25%削減できました。Jevと実行LLMのSkill選択も、OpenAIで96.67%、Geminiで100%一致しています。
OpenAIモデルとの不一致も、「売上データを月別に集計し、前月比も計算する」という依頼に対して、正解ラベルとJevは `spreadsheets`、OpenAIは `data_analysis` を選んでおり、計算であれば`spreadsheets`が良さそうです。
このことから、JevはSkill選択においては、かなり高い信頼性を持ち、実行速度やコストパフォーマンスの観点からも、かなり有用な選択肢になると思います。
これまでは、LLMにInputからOutputまでを実行させてましたが、Jevをはさみ効率化することが有用となりそうです。
ただ、個人的にはJevのようなものをOpenAI,AnthropicなどのAIプロバイダーが製品に組み込んでいくのではないか、と予想します。
いずれによせ、まだまだLLM/AI分野の発展は続きそうです。
