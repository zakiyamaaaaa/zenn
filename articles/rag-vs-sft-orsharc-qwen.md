## はじめに（TL;DR）

LLMの性能を上げる方法としてRAGとFine-tuningがあります。それらがどのように異なるのか、そして正解率に対してどのような結果になるのか、を今回は実験して確かめてみました。実験環境は、Google Colab の T4 GPU、仕様したモデルはQwen2.5-1.5B-Instruct を使いました。

題材は公開データセット [OR-ShARC](https://github.com/Yifan-Gao/open_retrieval_conversational_machine_reading) の「規則に照らして yes / no / 追加質問（inquire）を判断するタスク」です。同じ test 250 件で、何もしない Base、RAG、SFT、SFT＋RAG を比較しました。

結果をまとめると次のとおりです。

![正式評価の正解率](/images/rag-vs-sft-orsharc-qwen/orsharc_formal_accuracy.png)

- SFT を入れた条件はどれも約 57〜60% で、最も高かったのは「学習時から検索文書を見せた SFT＋RAG」の 59.6% でした。ただし SFT 単独（56.8%）との差は 7 件と小さく、意味のある差だとは言い切れません。
- Base（Qwenモデルのみ）での正答率は、2.4% 、 RAGと組み合わせた場合は0.4% でした。原因の多くは、回答の JSON を Markdown のコードフェンスで囲んでしまう形式違反です。フェンスだけを外して採点し直すと 39.2% と 41.6% になります。
- 一番の学びは、検索付き SFT の正解率が一時 21.6% まで落ちた原因でした。推論時だけ JSON の先頭に `{` を強制入力していたため、学習時とトークン列がずれていたのです。これを直すと 57.2% まで戻りました。

「RAG を足せば良くなる」「SFT＋RAG なら一番良い結果となる」とは限らず、学習と推論で入出力の形をそろえることが結果を大きく左右した、というのが実感です。

また、STF+RAGでも、どのように学習するかで結果が微妙に異なるということも今回の実験でわかりました。

## SFT と RAG の違い


|        | RAG（検索拡張生成）                            | SFT（教師ありファインチューニング）    |
| ------ | -------------------------------------- | ---------------------- |
| 何を変えるか | 推論時の入力（関連文書を検索してプロンプトに足す）              | モデルの重み（入力と正解の組で追加学習する） |
| 得意なこと  | 最新・大量の知識を、学習し直さずに参照させる                 | 回答の形式や判断の癖をモデルに覚えさせる   |
| 弱点     | 検索を外すと逆にノイズになる。渡された文書をモデルが使いこなせるとは限らない | 学習コストがかかる              |


素直に考えると、「SFT で判断の仕方と出力形式を覚えさせ、RAG で根拠になる規則を渡す」組み合わせが一番良さそうです。本記事ではこれも含めて検証します。

さらに SFT＋RAG には 2 種類の作り方があります。

- **文書なしで学習**：SFT は相談内容だけで学習し、推論時にだけ検索文書を足す
- **検索文書付きで学習**：学習時から検索文書を入力に含めておく

後者の方が「文書を読んで判断する」練習になるはずなので、この違いも比較しました。

## 実験内容



### 前提

- 実行環境：Google Colab（T4 GPU、16GB）、成果物は Google Drive に保存
- モデル：Qwen/Qwen2.5-1.5B-Instruct（4bit NF4 量子化）
- 学習：QLoRA（Transformers / PEFT / TRL / bitsandbytes）
- 検索：ローカル Embedding（multilingual MiniLM-L12-v2）＋ FAISS
- 有料 API・API キーは使っていません。seed は 42 に固定しました

![プログラムの構成](/images/rag-vs-sft-orsharc-qwen/orsharc_architecture_ja.png)

### データセット

最初は EC サイトの返品・保証判定を題材にした架空データを自作して実験しました。しかし正解ラベルを自分で作っているため、結果の信頼性に限界があります（このときは SFT 60.0% に対し SFT＋RAG が 29.2% と、組み合わせると大きく下がる結果でした）。

そこで、公開されている規則判定データセット **OR-ShARC**（[論文](https://arxiv.org/abs/2102.08633)、[公式リポジトリ](https://github.com/Yifan-Gao/open_retrieval_conversational_machine_reading)）に切り替えました。行政手続きのページなどの規則文書をもとに、ユーザーの相談に答える会話型のタスクです。

- 入力：`question`（質問）、`scenario`（状況）、`history`（それまでの追加質問と回答）
- 出力：`yes` / `no` / `inquire`（情報が足りないので追加質問する）
- 件数：公式データから seed 42 で train 600 / validation 150 / test 250 件を抽出
- 検索対象：規則文書 651 件

データの例です（test より、正解は `yes`）。

```json
{
  "question": "Can I apply zero VAT to this item?",
  "scenario": "The item is not equipment for audio books or newspapers, and I'm not selling lifeboats or anything related to that. It's for medicine and medicinal ingredients.",
  "history": [
    {"follow_up_question": "Is it equipment for making ‘talking’ books and newspapers?", "follow_up_answer": "No"},
    {"follow_up_question": "Are you selling lifeboats and associated equipment, including fuel?", "follow_up_answer": "No"},
    {"follow_up_question": "Are you selling medicine or ingredients for medicine?", "follow_up_answer": "Yes"}
  ]
}
```

モデルには、正解ラベルや正解文書の ID は渡していません。

### 比較条件


| 条件                | 推論時の入力            | 使うモデル            |
| ----------------- | ----------------- | ---------------- |
| Base              | 相談内容のみ            | 基礎モデル            |
| RAG               | 相談内容＋検索文書（上位 3 件） | 基礎モデル            |
| SFT               | 相談内容のみ            | 文書なしで学習したアダプター   |
| SFT＋RAG（文書なし学習）   | 相談内容＋検索文書         | 文書なしで学習したアダプター   |
| SFT＋RAG（検索文書付き学習） | 相談内容＋検索文書         | 検索文書付きで学習したアダプター |


学習設定は、600 件・1 epoch（75 回の更新）、batch size 2、勾配蓄積 4、学習率 2e-4、LoRA rank 16 / alpha 32 / dropout 0.05 です。T4 で約 23 分かかりました。

### 評価方法

モデルには、次の形の JSON だけを返すよう指示しました。

```json
{"decision":"yes|no|inquire","follow_up_question":""}
```

採点は LLM を使わず、Python で次のように行います。

- JSON として正しく読めること、キーが 2 つだけであること、yes / no のときは `follow_up_question` が空であること。これを満たさない回答は形式違反として**不正解**にします
- `decision` が公式の正解ラベルと一致すれば正解
- 指標は正解率、macro F1、形式適合率

`inquire` のときの追加質問の中身が正解の質問と同じ意味かどうかは、正解率に含めていません。

## 結果



### 全条件の比較

同じ test 250 件での結果です。「フェンス除去診断」は、回答全体を囲む Markdown のコードフェンスを 1 組だけ外して採点し直した参考値です（JSON の中身は変更していません）。


| 条件                | 正式評価             | フェンス除去診断     | macro F1（正式） | 形式適合（正式） |
| ----------------- | ---------------- | ------------ | ------------ | -------- |
| Base              | 2.4%（6 件）        | 39.2%（98 件）  | 0.045        | 4.8%     |
| RAG               | 0.4%（1 件）        | 41.6%（104 件） | 0.007        | 3.2%     |
| SFT               | 56.8%（142 件）     | 56.8%        | 0.570        | 99.6%    |
| SFT＋RAG（文書なし学習）   | 57.6%（144 件）     | 57.6%        | 0.577        | 100%     |
| SFT＋RAG（検索文書付き学習） | **59.6%（149 件）** | 59.6%        | 0.595        | 100%     |


![正式評価の正解率](/images/rag-vs-sft-orsharc-qwen/orsharc_formal_accuracy.png)

SFT の 3 条件はどの評価方法でも同じ値で、RAG を足した効果は 1〜3 ポイント程度でした。

### Base / RAG が極端に低い理由：コードフェンス

Base では 250 件中 229 件、RAG では 235 件が、次のようにコードフェンスで囲まれていたために形式違反になっていました。

```text
```json
{
  "decision": "no",
  "follow_up_question": ""
}
```
```

プロンプトで「Markdown のフェンスを付けないこと」と指示していても、基礎モデルはチャットでの癖どおりに囲んでしまいます。SFT を入れると、ほぼ 100% 指定どおりの形式で返すようになりました。

つまり、SFT の大きな改善の一部は「判断が賢くなった」ことではなく「出力形式が安定した」ことによるものです。フェンス除去診断で比べると、Base / RAG の約 40% に対して SFT は約 57%。判断そのものの改善は、正式評価の差より小さいと読むべきです。

なお、フェンス除去診断は結果を見てから追加した分析なので、正式評価の値を置き換えるものではありません。

### SFT＋RAG：学習時に文書を見せるかどうか


| SFT＋RAG の作り方        | 正解率          |
| ------------------- | ------------ |
| 文書なしで学習し、推論時だけ文書を足す | 57.6%（144 件） |
| 学習時から検索文書を入力に含める    | 59.6%（149 件） |


学習時から文書を見せた方が 5 件多く正解しました。ただし、後述の修正（損失を回答部分だけにかける、EOS の修正）も同時に入っているため、純粋に「文書の有無」だけの効果ではありません。

## ハマりどころ：JSON の先頭を強制入力したら正解率が 21.6% に落ちた

検索文書付きで学習した SFT＋RAG を最初に評価したとき、正解率は 21.6%、形式適合は 38.8% しかありませんでした。原因を調べると、次の 3 つの問題が見つかりました。

### 1. 学習時と推論時で JSON 先頭のトークンが違った

推論時、「JSON で答えやすくするため」に、assistant の回答の先頭へ `{` を強制入力（プリフィル）していました。

一方、学習時は完成した JSON をそのまま回答として与えています。Qwen のトークナイザーでは、学習データ側の先頭の `{"` が 1 トークンになりますが、推論時に強制入力した `{` 単独は別のトークンです。見た目の文字列は同じでも、モデルにとっては学習時に見たことのない書き出しになっていました。実際に確認すると、学習データ 600 件すべてで先頭のトークン列が一致していませんでした。

その結果、`{"decision":"no", "follow_up_question":"Do you have an honorable discharge?"}` のように、yes / no と追加質問を同時に出す形式違反が増えていました。

### 2. 入力文書まで学習していた

学習データを 1 本のテキスト（指示＋相談＋検索文書＋正解）として渡していたため、実際の TRL の設定では全文に損失がかかっていました。検索文書を足すと入力が長くなり、回答部分が損失全体に占める割合は約 4% まで下がります。

修正後は prompt と completion を分け、`completion_only_loss=True` で回答部分だけに損失をかけるようにしました。実際のバッチで確認すると、例えば 487 トークン中 476 トークンの入力がマスクされ、回答の 11 トークンだけが学習対象になっていました。

### 3. EOS が二重に付いていた

正解の末尾に自分で EOS を付けたうえ、チャットテンプレートも終端を付けていました。テンプレート側に任せて 1 つにしました。

### 修正の効果


| 段階                 | 正解率   | 形式適合  |
| ------------------ | ----- | ----- |
| 修正前（強制入力あり）        | 21.6% | 38.8% |
| 同じアダプターで、強制入力だけやめる | 57.2% | 100%  |
| 学習も修正して新しく学習し直す    | 59.6% | 100%  |


大幅な回復は推論側の修正だけで起きています。学習側の修正による上積みは 2.4 ポイント（6 件）でした。

教訓は「推論時の工夫を入れるなら、学習時も同じ形にする」です。プリフィルは便利ですが、SFT と組み合わせるとトークン単位でずれる可能性があります。

なお、Base / RAG にとっては強制入力がコードフェンスを抑える効果もあったため、外したことで前述のフェンス問題が表に出ました。同じ変更でも、モデルによって良い方にも悪い方にも働きます。

## 考察と限界

- **RAG があまり効かなかった理由**：学習データで、正解の規則文書が検索の上位 3 件に入ったのは 72.8% でした。残りの約 4 分の 1 では関係の薄い文書を渡していたことになります。また 1.5B のモデルでは、渡された規則を正しく当てはめる力自体が限られている可能性があります。最初の EC データでは検索の再現率が 99.2% でも RAG で下がっており、「正しい文書を渡せば正しく使える」とは限りません。
- **数件の差は有意とは言えない**：検索文書付き学習の新旧比較（143 件 → 149 件）で McNemar 検定を行うと p ≈ 0.307 でした。250 件・seed 1 回では、数件の差は誤差の範囲と考えるべきです。
- **seed によるばらつき**：LoRA による学習では、seed による正解率の標準偏差は数ポイント程度という報告があります（[arXiv:2503.07329](https://arxiv.org/abs/2503.07329)）。SFT の有無による大きな差は seed の影響を超えていると考えられますが、SFT＋RAG の作り方による 2〜3 ポイントの差は、その範囲に収まる可能性があります。
- **SFT の効果には形式の安定化が含まれる**：前述のとおり、判断能力の向上だけを測った値ではありません。
- **追加質問の質は未評価**：`inquire` と判断できたかどうかだけを見ており、聞き返した質問の内容が適切かは評価していません。
- **規模が小さい**：1.5B モデル、600 件、1 epoch です。モデルサイズや学習量、検索の品質を変えれば結論が変わる可能性があります。



## まとめ

- 小さな LLM では、SFT の効果が大きく（約 57〜60%）、RAG の上積みは 1〜3 ポイント程度でした。
- SFT＋RAG は、学習時から検索文書を見せた方がわずかに良い結果でしたが、有意な差とまでは言えません。
- Base / RAG の低い正式スコアは、主にコードフェンスによる形式違反が原因でした。評価では、形式の正しさと判断の正しさを分けて見る必要があります。
- 学習と推論でトークン列がずれると、SFT の結果が大きく崩れます。プリフィルなどの推論時の工夫は、学習データの形とそろえることが重要です。

今後は、より大きなモデルを教師にして小さなモデルへ回答を学ばせる「蒸留」や、検索精度の改善、モデルサイズを変えた比較を試してみたいと考えています。
